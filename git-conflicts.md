# git-conflicts.md — конфликты в общем репозитории группы

Работа в общем репо группы на парах почти гарантированно приведёт к `non-fast-forward`.
Это **нормально**: это не потерянная работа, а сигнал «кто-то уже отправил свои правки».
Здесь — самый короткий маршрут назад.

## 1. Правило: pull только с --rebase

Перед каждым коммитом забирайте чужие правки **поверх** своих (без merge-коммитов):

```bash
git pull --rebase
```

Если git ругается «Your branch is ahead / diverged от origin» — не паникуйте, это и есть
нормальное состояние после чьей-то правки.

## 2. Push отвергнут: non-fast-forward

```
! [rejected]        main -> main (non-fast-forward)
hint: Updates were rejected because the remote contains work that you do not have locally.
```

Что случилось: кто-то уже запушил в `main` после вашего локального коммита.
Что делать:

```bash
git pull --rebase      # применит ваши коммиты ПОВЕРХ чужих
git push
```

## 3. Наезд на чужие правки: merge-коммит

Если кто-то неаккуратно сделал `git pull` (без `--rebase`), в истории появится
merge-коммит вида `Merge branch 'main' of ...`. Он не опасен, но мешает истории:

```bash
git log --oneline --graph    # увидите развилку
git pull --rebase            # перепишет ваши коммиты поверх — merge-коммит исчезнет
git push
```

## 4. Конфликт файла (только в вашей лабе)

Если conflict возникает в файле, где работаете ТОЛЬКО вы (ваша подпапка `<Фамилия>/`) —
значит вы случайно отредактировали то, что правил сосед, или скопировали его скелет.
Порядок:

```bash
git status                                    # какие файлы конфликтут
git diff                                       # что именно «спорит»
# отредактируйте файл: оставьте свой вариант (ваша подпапка — ваша территория)
git add <файл>
git rebase --continue
git push
```

Помните: вы работаете ТОЛЬКО в `lab-NN/<Фамилия>/`. Если конфликт в чужой подпапке —
не трогайте его, оставьте чужой вариант (замечание в сообщении коммита).

## 5. «Я не я, коммит не мой»: как убрать чужой коммит (только если уверены)

```bash
git log --oneline -5
git reset --soft HEAD~1        # вернуть изменения в рабочую папку (коммит «снят»)
# или
git revert HEAD                # сделать обратный коммит (безопасный, если уже запушен)
```

Перед любым `reset --hard` — ДВАЖДЫ проверьте, что вы не стираете чужую работу.

## 6. «Всё сломалось»: быстрый откат к известному состоянию

```bash
git checkout <тег>    # например lab-05 — веха курса (ставит преподаватель)
# или вернуться к последнему своему коммиту:
git log --oneline && git reset --hard <хеш>
```

Теги `lab-NN` и `v1.0` ставит преподаватель: они фиксируют состояние СРЕЗА курса,
которое можно всегда переоткрыть заново.

## Чек-лист перед каждым коммитом

```bash
git status          # нет ли «чужих» изменений рядом
git pull --rebase   # забрать правки группы
git add lab-NN/<Фамилия>/
git commit -m "..."
git push            # если rejected — см. п.2, это нормально
```
