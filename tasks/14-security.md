# Лабораторная работа №14 — Защита веб-приложения

**Тема:** валидация, SQL-инъекции, XSS, CSRF и защита данных.
**Цель:** сделать блог устойчивым к типовым атакам и не раскрывать секреты.

## Краткая теория
- **XSS** — внедрение скриптов через пользовательский ввод. Защита: экранировать **всё** при выводе: `htmlspecialchars($value, ENT_QUOTES, 'UTF-8')`. Никогда не выводить ввод без экранирования (`$_POST`, `$_GET`, данные БД).
- **SQL-инъекция** — пользователь «дописывает» SQL через параметры. Защита: только **prepared statements** + привязка параметров; никогда не вставлять значения прямо в строку запроса.
- **CSRF** — атака «от имени авторизованного пользователя»: ваша форма с изменением данных должна содержать случайный токен, проверяемый на сервере.
- **Пароли:** `password_hash($pass, PASSWORD_DEFAULT)` при создании аккаунта, `password_verify()` при входе. Никогда не хранить пароли открыто (сейчас в `schema.sql` намеренно лежит `admin123` — заменить!).
- **Секреты:** доступы к БД в `.env`, который в `.gitignore`.
- **Валидация** — и клиентская (удобство), и серверная (безопасность): фильтры (`FILTER_VALIDATE_*`), `ctype_digit`, whitelist, лимиты длин.

## Ход работы
1. **SQL-инъекции.** Найдите ВСЕ запросы с подстановкой значений. Каждый замените на prepared statement (`prepare`/`execute` с плейсхолдерами `?` или `:name`). Проверьте особенно: `view.php?id=`, поиск, категории.
2. **XSS.** Введ̆ите в README и примените правило: каждый вывод из БД/GET/POST — через `e()`. Проверьте страницы `view.php`, списки, формы, комментарии (если выводите их).
3. **CSRF.** В `includes/functions.php` добавьте:
   - `$_SESSION['csrf'] = bin2hex(random_bytes(32));` (генерация);
   - функция `csrf_field()` — скрытое `<input name="csrf">`;
   - `verify_csrf()` — сравнение на сервере.
   Добавьте токен во все POST-формы (добавление/редактирование/удаление) и проверку в обработчиках. Начните сессию `session_start()`.
4. **Пароли.** Создайте страницы регистрации и входа (`register.php`, `login.php`), таблица `users` готова. Храните `password_hash()`. В `schema.sql` замените «пароль admin123» на комментарий-предупреждение и реальный хеш не храните в схеме.
5. При удалении блога убедитесь, что доступ к формам/операциям только для вошедших (минимальная простая проверка `$_SESSION['user_id']`). Полноценные роли — по желанию.
6. Проверьте повторно: в `.gitignore` есть `.env`, в репозитории нет реальных паролей/токенов. Напишите в README, какие меры защиты реализованы и как вы их проверили.

## Самопроверка

- Чем опасен запрос `SELECT * FROM posts WHERE id = $_GET['id']`? Покажите, что введёт атакующий.
- Зачем токен CSRF, если форму видят только свои?
- Почему `password_hash` нельзя «вычислить» обратно и что будет, если хеш украдут из БД?

## Критерий «зачтено»
- Все SQL-обращения — prepared statements (в коде нет ни одной строковой подстановки).
- Весь вывод экранирован функцией `e()`; XSS-попытка из формы не «срабатывает».
- Все POST-формы защищены CSRF-токеном с проверкой.
- Пароли хранятся только хешированными; секреты — только в `.env`.
- В README — раздел «Безопасность» с перечнем проверок.
